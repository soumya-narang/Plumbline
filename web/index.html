How it works

Three ideas, one graph

Follow the path

Every exposed service comes with the exact chain from its own dependency to the poisoned version, found with a shortest-path query, and a receipt you can re-derive.

1. The lockfile has not changed

keyv@6.0.1 is not on the advisory

No longer true since 12:45

Say what you assumed

Clearing a service rests on facts: the lockfile hasn't changed, this version isn't on the advisory. Plumbline stores each fact next to the decision that leans on it.

Reopen only what broke

When a fact stops being true, one query finds the decisions that leaned on it. Everything else stays decided, so nothing is re-reviewed by habit.

The graph

Take FalkorDB away and there is nothing left

Evidence, memory and the agent's tools all run on one FalkorDB graph. This is what it does.

Evidence
A shortest-path query over the resolved dependency edges returns the chain for every exposed service.
Memory
Decisions point at the facts they assume. One traversal finds exactly which decisions a new event breaks.
Tools
An MCP server exposes read-only tools, including a fleet-wide fix-first query and PageRank over each dependency graph. The agent reaches the graph only through them.
